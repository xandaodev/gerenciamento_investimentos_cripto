## Project

CriptoVision API: a Spring Boot REST API that tracks a user's crypto buy/sell transactions and works out average price, unrealized PNL, the portfolio summary and DCA/sell simulations, using Binance market data. The codebase, identifiers, commit messages and docs are in **Portuguese**, so keep new code and messages in Portuguese. Commits follow Conventional Commits (`feat:`, `fix:`, `test:`).

Stack: Java 25, Spring Boot 4 (`spring-boot-starter-webmvc`, `-restclient`), Spring Data JPA, Flyway, Spring Security with stateless JWT (`com.auth0:java-jwt`), MySQL, and springdoc OpenAPI.

`docs/ARCHITECTURE.md` and `docs/BUSINESS_RULES.md` hold the detailed reference for the financial formulas, endpoint flows and known technical debt (ARCHITECTURE §15). If they disagree with the code, trust the code. Update them, and the README, whenever you change behavior or rules (principle #10 in BUSINESS_RULES).

## Visão do produto

O CriptoVision é o principal projeto pessoal do autor. O objetivo é transformá-lo num produto sólido e publicá-lo para usuários reais. Por isso, segurança, confiabilidade dos cálculos financeiros e qualidade do código têm prioridade sobre velocidade de entrega.

## Commands

Use the Maven wrapper (`.\mvnw.cmd` on Windows, `./mvnw` elsewhere):

```bash
./mvnw clean verify                                 # full suite: unit + MySQL integration tests (what CI runs, on JDK 25; needs Docker)
./mvnw clean test                                   # fast suite: unit/H2 tests only, no Docker needed
./mvnw test -Dtest=CarteiraServiceTest              # single test class
./mvnw test -Dtest=CarteiraServiceTest#nomeDoMetodo # single test method
./mvnw verify -Dit.test=MigracoesMysqlIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false  # single integration test class
./mvnw spring-boot:run                              # run locally (needs MySQL + env vars)
./mvnw clean package && docker compose up --build   # dev: API on http://localhost:8080, no HTTPS (Dockerfile copies target/*.jar, so package first)
docker compose --profile producao up -d --build     # production (VPS): adds Caddy with HTTPS for DOMINIO on 80/443
```

Runtime env vars (see `.env.example`): `DB_USER`, `DB_PASSWORD`, `JWT_SECRET` (required), plus `MYSQL_ROOT_PASSWORD` for Compose, `CORS_ALLOWED_ORIGINS` (required in production), `BINANCE_API_BASE_URL` and `COTACOES_*` timeouts/TTL. Locally the datasource points to `localhost:3306/criptovision`. Docker Compose publishes MySQL on `127.0.0.1:3307` and the API on `127.0.0.1:8080` (never on all interfaces: Docker bypasses `ufw`). The `producao` profile adds Caddy (`Caddyfile`, needs `DOMINIO`), which terminates TLS and proxies to `api:8080`. The API runs there with `SERVER_FORWARD_HEADERS_STRATEGY=native`, so per-IP limits and HSTS see the real client. Outside Compose that property stays `none`, so clients can't spoof `X-Forwarded-For`. The DB connection uses TLS: MySQL runs with `--require-secure-transport=ON` (self-signed cert auto-generated by MySQL 8) and the API connects with `sslMode=REQUIRED` and no `allowPublicKeyRetrieval`. Don't reintroduce `useSSL=false`, because it maps to `sslMode=DISABLED`. The Testcontainers MySQL in `MysqlContainerConfiguration` mirrors this setup, and `ConexaoSeguraMysqlIT` checks it. The VPS deploy steps are in the README. Swagger UI is served at `/swagger-ui.html`.

## Architecture

Base package `br.com.criptovision`: controller → service → repository, plus `security`, `exception`, `dto`, `config` and the `cotacao` subsystem.

**Transaction history is the single source of truth.** Balances and average prices are never persisted. `Carteira` (a `Map<String, Moeda>`) and `Moeda` are in-memory objects. `CarteiraService.reconstruirCarteira` rebuilds them on every request by replaying the user's transactions, sorted by `data` and then `id` (it sorts a copy defensively). Consequences:
- `atualizarTransacao` and `excluirTransacao` first simulate the change on a *copy* of the history. They touch the managed entity only if the replay stays valid. Otherwise they throw `AlteracaoHistoricoInvalidaException` → 409.
- **Concurrency:** create, update and delete run their DB phase through `executarComHistoricoBloqueado`, a `TransactionTemplate` whose first query is `UsuarioRepository.bloquearPorId`, a `SELECT ... FOR UPDATE` on the user's row. This serializes writes per user, so two simultaneous sells can't both pass the balance check. The lock must stay the first query of the transaction, because under MySQL REPEATABLE READ the read snapshot is taken at the first plain read. Binance ticker validation runs *before* the transaction so the lock is never held during an HTTP call. The two-sells scenario lives in `CenarioConcorrenciaTransacoes` and runs twice with real threads: `ConcorrenciaTransacoesTest` on H2 and `ConcorrenciaTransacoesMysqlIT` on real MySQL. Only the MySQL run catches a plain read placed before the lock.
- A sale larger than the balance throws `SaldoInsuficienteException`. A replay failure on persisted data throws `HistoricoInconsistenteException` → 500. Invalid transactions must never be skipped silently.
- Create, update and delete must go through `CarteiraService`, never straight to the repository from controllers.

**Per-user isolation.** Controllers get the `Usuario` entity via `@AuthenticationPrincipal` (set by `SecurityFilter` from the JWT) and pass it down. Every repository query filters by user. Accessing another user's transaction returns **404, not 403**, so the API never reveals that the ID exists. `Transacao.usuario` is `@JsonIgnore`d. The request DTO has no user/id/date fields. Public routes: `/auth/login`, `/auth/register` and the Swagger paths. CORS origins come from `CORS_ALLOWED_ORIGINS` (comma-separated, bound and validated at startup by the `CorsProperties` record; invalid origins stop the app). They default to `localhost:5173/5174` (the Vite frontend), and a configured list replaces the defaults.

**Brute-force protection.** `AutenticacaoController` calls `ProtecaoForcaBruta` before authenticating or registering: login attempts per IP, failed logins per (normalized) login, and registrations per IP, each a fixed-window `LimiteDeTentativas` (in-memory Caffeine counters, atomic per key, time from the `Clock`). Over the limit → `TentativasExcedidasException` → 429 with `Retry-After`, with the same message whatever the limit, so it never reveals whether an account exists. Limits come from `seguranca.tentativas.*` (`TentativasProperties`). The `test` profile sets them very high so other tests aren't throttled, and `ProtecaoForcaBrutaHttpTest` lowers them in its own context. The IP is `getRemoteAddr()`, so behind a proxy it needs `server.forward-headers-strategy`.

**Quotes (`cotacao` package).** `CotacaoService` → `CotacaoClient` (interface; `BinanceCotacaoClient` implementation using Spring `RestClient` against `binance.api.base-url`, default `data-api.binance.vision`) + `CotacaoCache` (in-memory, with a fresh TTL `cotacoes.cache.ttl` and a stale-fallback window `cotacoes.cache.max-stale`). Behavior:
- It batch-fetches the pending tickers, falls back to per-ticker requests on `TickerInvalidoException`, and falls back to stale cached quotes on `ServicoCotacaoIndisponivelException`.
- `ResultadoCotacoes` carries the found quotes plus the `indisponiveis` tickers. The summary degrades per asset (`ResumoAtivoDTO.semCotacao`) instead of failing.
- `USDT` is hard-coded to price 1 with 0% change. `TickerNormalizer` maps names like BITCOIN→BTC.
- Never turn provider failures into a zero price. Unknown ticker → 400; provider down with no fallback → 503.
- A `Clock` bean (`CotacaoConfiguration`) is injected for time-dependent logic, so tests can control time.

**Money.** Use `BigDecimal`. `Moeda` keeps the exact `custoTotal` (buys add `quantidade × preço` with no rounding; a partial sale scales it by the remaining balance at 34 significant digits; a full sale zeroes it). The average price is derived on read (`custoTotal ÷ saldo`, scale 18, `HALF_UP`) and must never be fed back into the next transaction. Migration `V3` widened the DB precision. Some simulation and total methods still use `double`, which is known debt, so don't add new `double` math.

**Errors.** `GlobalExceptionHandler` returns RFC 7807 `ProblemDetail` responses (with field errors for validation). `AutenticacaoEntryPoint` handles 401s. New business exceptions should get a handler there.

**Database.** Flyway migrations live in `src/main/resources/db/migration` (`V<n>__descricao.sql`), with `ddl-auto=validate`. Schema changes need a new migration, and the entity must match it.

## Tests

- Two kinds of tests:
  - `*Test.java` (surefire, `mvn test`) use the `test` profile (`src/test/resources/application-test.properties`): H2 in MySQL mode with `ddl-auto=create-drop`, **Flyway disabled**, a fixed JWT secret, and the Binance URL pointed at `http://localhost`.
  - `*IT.java` (failsafe, `mvn verify`, package `integracao`) use the `integracao` profile against a real MySQL 8 started by Testcontainers (`MysqlContainerConfiguration`, a single `mysql:8.0` container shared via `@ServiceConnection`), with **Flyway enabled** and `ddl-auto=validate`, like production. `MigracoesMysqlIT` checks the migrations and column precision. Anything that depends on real MySQL behavior (migrations, locking, isolation, collation) belongs here, not in H2.
- Test styles in use:
  - pure Mockito unit tests (`@ExtendWith(MockitoExtension.class)`)
  - `@DataJpaTest` for repositories
  - `@SpringBootTest` + MockMvc HTTP tests that authenticate real users with JWT (e.g. `IsolamentoTransacoesHttpTest`, which uses `@MockitoBean` for quotes)
  - `MockRestServiceServer` for `BinanceCotacaoClient`
- Never hit the real Binance API in tests: mock `CotacaoClient`/`CotacaoService`.
- Most service and controller tests live in the `br.com.criptovision.test` package. Newer ones mirror the main package layout (e.g. `cotacao/`).
