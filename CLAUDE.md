## Project

CriptoVision API: a Spring Boot REST API that tracks a user's crypto buy/sell transactions and works out average price, unrealized PNL, the portfolio summary and DCA/sell simulations, using Binance market data. The codebase, identifiers, commit messages and docs are in **Portuguese**, so keep new code and messages in Portuguese. Commits follow Conventional Commits (`feat:`, `fix:`, `test:`).

Stack: Java 25, Spring Boot 4 (`spring-boot-starter-webmvc`, `-restclient`), Spring Data JPA, Flyway, Spring Security with stateless JWT (`com.auth0:java-jwt`), MySQL, and springdoc OpenAPI.

`docs/ARCHITECTURE.md` and `docs/BUSINESS_RULES.md` hold the detailed reference for the financial formulas, endpoint flows and known technical debt (ARCHITECTURE §15). If they disagree with the code, trust the code. Update them, and the README, whenever you change behavior or rules (principle #10 in BUSINESS_RULES).

## Visão do produto

O CriptoVision é o principal projeto pessoal do autor. O objetivo é transformá-lo num produto sólido e publicá-lo para usuários reais. Por isso, segurança, confiabilidade dos cálculos financeiros e qualidade do código têm prioridade sobre velocidade de entrega.

## Commands

Use the Maven wrapper (`.\mvnw.cmd` on Windows, `./mvnw` elsewhere):

```bash
./mvnw clean verify                                 # full suite: unit + MySQL integration tests (what CI runs, on JDK 25; needs Docker)
./mvnw clean test                                   # fast suite: unit/H2 tests only, no Docker needed
./mvnw test -Dtest=CarteiraServiceTest              # single test class
./mvnw test -Dtest=CarteiraServiceTest#nomeDoMetodo # single test method
./mvnw verify -Dit.test=MigracoesMysqlIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false  # single integration test class
./mvnw spring-boot:run                              # run locally (needs MySQL + env vars)
docker compose up --build                           # dev: API on http://localhost:8080, no HTTPS (multi-stage Dockerfile builds the JAR itself; no local Java needed)
bash scripts/testar-stack.sh                        # smoke test of the production image + compose stack (isolated project and ports; CI runs it too)
docker compose --profile producao up -d --build     # production (VPS): adds Caddy with HTTPS for DOMINIO on 80/443, plus the daily backup
docker compose --profile backup up -d --build       # local: db + api + backup service, without Caddy
```

Runtime env vars (see `.env.example`): `DB_USER`, `DB_PASSWORD`, `JWT_SECRET` (required), plus `MYSQL_ROOT_PASSWORD` for Compose, `CORS_ALLOWED_ORIGINS` (required in production), `BINANCE_API_BASE_URL`, `COTACOES_*` timeouts/TTL, `MANAGEMENT_SERVER_PORT`/`MANAGEMENT_SERVER_ADDRESS` (Actuator, default `8081` on `127.0.0.1`) and `JPA_SHOW_SQL` (default `false`). Locally the datasource points to `localhost:3306/criptovision`. Docker Compose publishes MySQL on `127.0.0.1:3307` and the API on `127.0.0.1:8080` (never on all interfaces: Docker bypasses `ufw`). The `producao` profile adds Caddy (`Caddyfile`, needs `DOMINIO`), which terminates TLS and proxies to `api:8080`. The API runs there with `SERVER_FORWARD_HEADERS_STRATEGY=native`, so per-IP limits and HSTS see the real client. Outside Compose that property stays `none`, so clients can't spoof `X-Forwarded-For`. The DB connection uses TLS: MySQL runs with `--require-secure-transport=ON` (self-signed cert auto-generated by MySQL 8) and the API connects with `sslMode=REQUIRED` and no `allowPublicKeyRetrieval`. Don't reintroduce `useSSL=false`, because it maps to `sslMode=DISABLED`. The Testcontainers MySQL in `MysqlContainerConfiguration` mirrors this setup, and `ConexaoSeguraMysqlIT` checks it.

**Backups.** The `backup` service (profiles `producao` and `backup`) is built from `backup/Dockerfile` (`mysql:8.0` + the rclone binary). All the logic is in `backup/backup.sh`: a daily `mysqldump` → gzip → gpg AES-256 with `BACKUP_SENHA`, checked (decrypt + `-- Dump completed`) before it is accepted. Then local retention, an optional rclone copy to an S3 bucket (`BACKUP_S3_*`, env-only config, `no_check_bucket`), a weekly restore test into a throwaway mysqld, and `restaurar` (requires `--confirmar`, backs up the current state first). Never send unencrypted data to the bucket, and never fail silently: no password → refuse to run; no bucket → a warning on every backup. The DB password is passed via `MYSQL_PWD`, because MySQL option files cut values at `#`. Keep the script `shellcheck`-clean and LF (`.gitattributes`). `BackupMysqlIT` builds the image and tests it against MySQL with TLS and an `rclone serve s3` bucket. The VPS deploy steps are in the README. Swagger UI is served at `/swagger-ui.html`.

**API image.** The `Dockerfile` is multi-stage. The `build` stage (JDK) runs `dependency:go-offline` on the pom first, so that layer stays cached, then packages with `-Dmaven.test.skip=true`, because CI already ran the tests. The `runtime` stage (`25-jre-alpine`) copies the four layers from `jarmode=tools extract --layers --launcher` and runs as UID `10001`, with root-owned files. Its `ENTRYPOINT` is in exec form (Java is PID 1, so SIGTERM triggers graceful shutdown) with `-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError` against the Compose `mem_limit` (`API_LIMITE_MEMORIA`, default `1g`). The `HEALTHCHECK` uses `wget` on the management port. `.dockerignore` is an allowlist (`pom.xml`, `mvnw`, `.mvn/`, `src/main/`), so `.env` and `.git` never enter the build context. In Compose, `db` has a `mysqladmin ping` healthcheck over TCP, and `api`/`backup` use `depends_on: condition: service_healthy`. Caddy depends only on the API having started, so HTTPS stays up if the API is unhealthy. `scripts/testar-stack.sh` checks all of this against the real compose file, in an isolated project (it uses `!reset`/`!override`, so it needs Compose ≥ 2.24). The `imagem` CI job runs it. Keep it `shellcheck`-clean.

## Architecture

Base package `br.com.criptovision`: controller → service → repository, plus `security`, `exception`, `dto`, `config` and the `cotacao` subsystem.

**Transaction history is the single source of truth.** Balances and average prices are never persisted. `Carteira` (a `Map<String, Moeda>`) and `Moeda` are in-memory objects. `CarteiraService.reconstruirCarteira` rebuilds them on every request by replaying the user's transactions, sorted by `data` and then `id` (it sorts a copy defensively). Consequences:
- `atualizarTransacao` and `excluirTransacao` first simulate the change on a *copy* of the history. They touch the managed entity only if the replay stays valid. Otherwise they throw `AlteracaoHistoricoInvalidaException` → 409.
- **Transaction date.** The client may send `data` (ISO 8601 with offset, `OffsetDateTime` in `TransacaoRequestDTO`). It is converted to UTC and stored as `LocalDateTime` (no `@CreationTimestamp`). `CarteiraService.resolverData` defaults it (now from the `Clock`, or the existing date on update), rejects the future beyond 1 minute and anything before 2009-01-03 (`DataTransacaoInvalidaException` → 400), and truncates to micros. Because dates can be backdated, `registrarNovaTransacao` replays the history *up to* the new date and processes the new transaction there (no balance → `SaldoInsuficienteException`, 400). Then it replays the whole history with it inserted (a later transaction breaking → 409). Never validate a new transaction only "on top" of the current balance.
- **Concurrency:** create, update and delete run their DB phase through `executarComHistoricoBloqueado`, a `TransactionTemplate` whose first query is `UsuarioRepository.bloquearPorId`, a `SELECT ... FOR UPDATE` on the user's row. This serializes writes per user, so two simultaneous sells can't both pass the balance check. The lock must stay the first query of the transaction, because under MySQL REPEATABLE READ the read snapshot is taken at the first plain read. Binance ticker validation runs *before* the transaction so the lock is never held during an HTTP call. The two-sells scenario lives in `CenarioConcorrenciaTransacoes` and runs twice with real threads: `ConcorrenciaTransacoesTest` on H2 and `ConcorrenciaTransacoesMysqlIT` on real MySQL. Only the MySQL run catches a plain read placed before the lock.
- A sale larger than the balance throws `SaldoInsuficienteException`. A replay failure on persisted data throws `HistoricoInconsistenteException` → 500. Invalid transactions must never be skipped silently.
- Create, update and delete must go through `CarteiraService`, never straight to the repository from controllers.

**Per-user isolation.** Controllers get the `Usuario` entity via `@AuthenticationPrincipal` (set by `SecurityFilter` from the JWT) and pass it down. Every repository query filters by user. Accessing another user's transaction returns **404, not 403**, so the API never reveals that the ID exists. `Transacao.usuario` is `@JsonIgnore`d. The request DTO has no user or id fields (the optional `data` is covered under "Transaction date" above). Public routes: `/auth/login`, `/auth/register`, `GET /saude` and the Swagger paths. CORS origins come from `CORS_ALLOWED_ORIGINS` (comma-separated, bound and validated at startup by the `CorsProperties` record; invalid origins stop the app). They default to `localhost:5173/5174` (the Vite frontend), and a configured list replaces the defaults.

**JWT and revocation.** `TokenService` (constructor-injected, uses the `Clock` bean) signs HMAC-SHA256 tokens with `iss`, `aud=criptovision-api`, `sub=login`, a `versao` claim and a 2-hour expiry. At startup it refuses a `JWT_SECRET` shorter than 32 bytes or equal to the `.env.example` placeholder. `Usuario.versaoToken` (migration `V4`) is compared with the token's `versao` in `SecurityFilter`. Incrementing it revokes every token of the user: `POST /auth/logout` does that, and `PUT /auth/senha` does it too and returns a fresh token. Both lock the user row (`bloquearPorId`). A wrong current password counts as a failed login for `ProtecaoForcaBruta`. Refresh tokens were evaluated and deliberately not added (see ARCHITECTURE §6). Tests build tokens with `tokenService.gerarToken(usuario)`.

**Brute-force protection.** `AutenticacaoController` calls `ProtecaoForcaBruta` before authenticating or registering: login attempts per IP, failed logins per (normalized) login, and registrations per IP, each a fixed-window `LimiteDeTentativas` (in-memory Caffeine counters, atomic per key, time from the `Clock`). Over the limit → `TentativasExcedidasException` → 429 with `Retry-After`, with the same message whatever the limit, so it never reveals whether an account exists. Limits come from `seguranca.tentativas.*` (`TentativasProperties`). The `test` profile sets them very high so other tests aren't throttled, and `ProtecaoForcaBrutaHttpTest` lowers them in its own context. The IP is `getRemoteAddr()`, so behind a proxy it needs `server.forward-headers-strategy`.

**Quotes (`cotacao` package).** `CotacaoService` → `CotacaoClient` (interface; `BinanceCotacaoClient` implementation using Spring `RestClient` against `binance.api.base-url`, default `data-api.binance.vision`) + `CotacaoCache` (in-memory, with a fresh TTL `cotacoes.cache.ttl` and a stale-fallback window `cotacoes.cache.max-stale`). Behavior:
- It batch-fetches the pending tickers, falls back to per-ticker requests on `TickerInvalidoException`, and falls back to stale cached quotes on `ServicoCotacaoIndisponivelException`.
- `ResultadoCotacoes` carries the found quotes plus the `indisponiveis` tickers. The summary degrades per asset (`ResumoAtivoDTO.semCotacao`) instead of failing.
- `USDT` is hard-coded to price 1 with 0% change. `TickerNormalizer` maps names like BITCOIN→BTC.
- Never turn provider failures into a zero price. Unknown ticker → 400; provider down with no fallback → 503.
- `ConsultaDeCotacoes` sits between `CotacaoService` (cache/fallback policy) and `CotacaoClient` (HTTP). It coalesces concurrent requests per ticker: a `ConcurrentMap` of in-flight `CompletableFuture`s, where the owner always completes them in a `finally`. It runs the per-ticker fallback on virtual threads, bounded by `cotacoes.individual.paralelismo`, with a total deadline `cotacoes.individual.tempo-maximo` (the MDC is copied, so the logs keep `requestId`). Every provider call goes through the Resilience4j `CircuitBreaker` bean from `CotacaoConfiguration.criarCircuitBreakerDaBinance`, which tests reuse. Only `ServicoCotacaoIndisponivelException` is recorded as a failure, `TickerInvalidoException` is ignored, and `CallNotPermittedException` maps to unavailable. A single pending ticker uses the single-symbol endpoint. `BinanceCotacaoClient` logs 451 (region block) as ERROR and 418/429 as WARN.
- A `Clock` bean (`CotacaoConfiguration`) is injected for time-dependent logic, so tests can control time.

**Money.** Use `BigDecimal`. `Moeda` keeps the exact `custoTotal` (buys add `quantidade × preço` with no rounding; a partial sale scales it by the remaining balance at 34 significant digits; a full sale zeroes it). The average price is derived on read (`custoTotal ÷ saldo`, scale 18, `HALF_UP`) and must never be fed back into the next transaction. Migration `V3` widened the DB precision. The DCA and sale simulators are `BigDecimal` and validate their `@RequestParam`s with `@Positive`/`@Digits`. A DCA with no position returns `null` for `pmAtual`/`diferencaPM`, and a sale with no balance throws `SemSaldoParaSimularException` (400). `/carteira/total` returns `TotaisCarteiraDTO`: `custoDasPosicoes` (sum of `Moeda.custoTotal` from the rebuilt wallet), `totalAportado` (all buys), `totalRecebidoEmVendas` (all sales) and `moeda` = `CarteiraService.MOEDA_DE_REFERENCIA` (`USDT`). All financial math is now `BigDecimal`. Never add `double` math.

**Errors.** `GlobalExceptionHandler` returns RFC 7807 `ProblemDetail` responses (with field errors for validation). `AutenticacaoEntryPoint` handles 401s. New business exceptions should get a handler there. Constraint violations on `@RequestParam`s raise `HandlerMethodValidationException`, which has its own handler (400 with `erros`). Without it, they would fall into the catch-all 500. Every error body (including the entry point's 401) carries `requestId`, and both 500 handlers call `MetricasCriptoVision.erroInterno`, so keep that in any new 500 handler.

**Observability (`observabilidade` package).** `IdentificadorRequisicaoFilter` (highest precedence, before Spring Security) puts a request ID in the MDC (`requestId`), the `X-Request-Id` response header and error bodies. It reuses a client-sent ID only if it matches `[A-Za-z0-9._-]{1,64}`, so nobody can write free text into the logs. Plain-text logs show it through `logging.pattern.correlation` (a `%replace`, because Spring Boot drops a trailing space in that value). Compose sets `LOGGING_STRUCTURED_FORMAT_CONSOLE=ecs` (JSON, `requestId` as a top-level field) and rotates every container's logs (`x-logs` anchor). The Actuator runs on a **separate management port** (`8081`, loopback only, never published by Compose or proxied by Caddy), with only `health`, `metrics` and `prometheus` exposed. Spring Security permits `EndpointRequest.toAnyEndpoint()` for that reason. The only public health is the `publico` group at `GET /saude` (`additional-path=server:/saude`, status only, includes `db`). `MetricasCriptoVision` publishes `criptovision.erros.internos` (tag `excecao`), `criptovision.tentativas.bloqueadas` (tag `limite`) and `criptovision.cotacoes.provedor.indisponivel` (tag `resultado`). Tags must stay low-cardinality: never IDs, tickers or logins. There is no active alert yet: the user chose to wait for a monitoring tool.

**Database.** Flyway migrations live in `src/main/resources/db/migration` (`V<n>__descricao.sql`), with `ddl-auto=validate`. Schema changes need a new migration, and the entity must match it.

## Tests

- Two kinds of tests:
  - `*Test.java` (surefire, `mvn test`) use the `test` profile (`src/test/resources/application-test.properties`): H2 in MySQL mode with `ddl-auto=create-drop`, **Flyway disabled**, a fixed JWT secret, and the Binance URL pointed at `http://localhost`.
  - `*IT.java` (failsafe, `mvn verify`, package `integracao`) use the `integracao` profile against a real MySQL 8 started by Testcontainers (`MysqlContainerConfiguration`, a single `mysql:8.0` container shared via `@ServiceConnection`), with **Flyway enabled** and `ddl-auto=validate`, like production. `MigracoesMysqlIT` checks the migrations and column precision. Anything that depends on real MySQL behavior (migrations, locking, isolation, collation) belongs here, not in H2.
- Test styles in use:
  - pure Mockito unit tests (`@ExtendWith(MockitoExtension.class)`)
  - `@DataJpaTest` for repositories
  - `@SpringBootTest` + MockMvc HTTP tests that authenticate real users with JWT (e.g. `IsolamentoTransacoesHttpTest`, which uses `@MockitoBean` for quotes)
  - `MockRestServiceServer` for `BinanceCotacaoClient`
- Never hit the real Binance API in tests: mock `CotacaoClient`/`CotacaoService`.
- Both test profiles set `management.server.port=0`, because cached `RANDOM_PORT` contexts would otherwise fight over `8081`. So HTTP tests never see the production management defaults: `ConfiguracaoDeProducaoTest` reads `application.properties` directly to lock them in (port `8081`, loopback, exposure list, `/saude` without details, `show-sql` off). `ObservabilidadeHttpTest` uses a real Tomcat with `@LocalManagementPort` and connects to `127.0.0.1` (the management port is IPv4 loopback only).
- Most service and controller tests live in the `br.com.criptovision.test` package. Newer ones mirror the main package layout (e.g. `cotacao/`).
